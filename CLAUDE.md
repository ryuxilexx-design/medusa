# Med.uz.ai — clinic management platform (demo MVP)

Product name in every UI text, document and export: **Med.uz.ai** (old name "Meduza" survives only in internal identifiers: `@meduza/*` packages, `meduza_session` cookie, `meduza.branch` storage key, DB/container names — do not rename those). UI languages: Uzbek Latin (source text), Uzbek Cyrillic (derived automatically) and Russian — chosen per person (see i18n below). In Uzbek use the typographic apostrophe `‘` (o‘, g‘) and `’` (ma’lumot), never ASCII `'`. Spec: `docs/MVP_TZ.md`; status and limits: `docs/DEMO_STATUS.md`; meeting runbook: `docs/DEMO_SCRIPT.md`.

## Layout

- `apps/api` — NestJS 11, prefix `/api/v1`, raw SQL via `pg` (no ORM). Controllers in `src/modules/*`, cross-cutting code in `src/core/*`.
- `apps/web` — Next.js 15 App Router, all pages are client components using TanStack Query; `/api/v1/*` is proxied to the API (`next.config.mjs` rewrites), so the browser never talks to :4000.
- `packages/contracts` — zod schemas, labels, money/phone helpers shared by API and web.
- `database/` — SQL migrations (`migrations/NNN_*.sql`, applied on API start), deterministic seed (`seed/build.ts`), reset/clock helpers (`src/index.ts`).
- `e2e/` — puppeteer-core scripts with the system Chrome; `run.mjs` starts an isolated stack.

## Commands

`npm run db:up` · `npm run start` (prod build, web :3000 / API :4000) · `npm run dev` · `npm run build` · `npm run typecheck` · `npm test` (298 API tests; `test/ops.test.mjs` = health, sliding sessions, body limits, CLI password reset; `test/audit.test.mjs` holds the regression tests of the 2026-10-20 audit — `docs/audit/`) · `npm run e2e` · `npm run db:reset` (wipes live demo data — needs explicit user intent) · `npm run db:backup` / `db:restore -- <file>` · `npm run db:readonly-role` · `npm run db:create-clinic -- …` (onboard a real clinic; prints a one-time temp password) · `npm run db:reset-password -- --login <phone|username> [--tenant <name|id>]` (operator's reset when the sole manager is locked out: new temp password shown once, lockout cleared, sessions closed) · `npm run db:import-icd10 -- file.csv` (official MKB-10 list) · `npm run db:import-drugs -- file.csv [--replace]` (official drug list, `docs/DRUGS.md`). `GET /api/v1/health` is the public health check (no session, no audit, no request log; 503 when the DB does not answer in 2 s) — the Dockerfile HEALTHCHECK and the uptime monitor use it.
Project skills: `meduza-run`, `meduza-demo-reset`, `meduza-deploy`, `meduza-verify` — use them for those tasks.

## Rules that are easy to break

- **Tenant & role come only from the server session** (`req.ctx`). Every query filters by `tenant_id`; another tenant's id must return 404, a forbidden action 403. Hiding a button is never the permission check — add the server check and a test.
- **Money is integer tiyin** (`bigint`, 1 so‘m = 100). Never sum money in floating point on the client; format with `formatSom`.
- **Time:** store UTC; display Asia/Tashkent (UTC+5, no DST). "Now" is the demo clock: SQL `demo_now()`, API `now()` from `core/clock.ts`, web `useSession().demoNow()`. Never use `now()`/`Date.now()` for business timestamps. Date filters are `[local day start, next local day start)`.
- **Writes that matter run in `db.tx`** with row locks (`FOR UPDATE`) where races are possible. Appointment overlap is enforced by a DB exclusion constraint (→ 409 `SLOT_TAKEN`); payments require `Idempotency-Key`; signed notes, verified lab results and payments are immutable via DB triggers.
- **Days off** (`schedule_exceptions`, migration 018): a doctor's `day_off`/`vacation`, a clinic or branch `holiday` (`doctor_id NULL`) or one-day `custom_hours` sit on top of the weekly `schedules` row. Only `booking.ts` reads them (`dayException()` inside `validateSlot`/`availability` → 409 `DOCTOR_UNAVAILABLE`, `working:false` + `reason`); the bot and the grid get them through those functions — never re-implement the check. Creating an exception never cancels bookings: the response lists `affected` and the registrar reschedules.
- **Status changes** are validated on the server; stale client state → 409 with a "refresh" message. Audit important actions with `audit()` (no clinical text, no AI prompts in audit).
- **Clinical data is doctor-only** (managers, cashiers and registrars never read clinical notes or result values). Lab values are visible to doctors only after verification.
- **No clinical or financial data in localStorage** — only UI preferences (selected branch).
- **Errors:** API returns `{error:{code,message,fields?},request_id}`; UI keeps the user's input on failure, shows the error, and never shows a success toast for an action that did not complete.
- **Auth:** staff sign in with `/auth/login` (phone or username + scrypt-hashed password; lockout after 5 failures; temp passwords force a change — the guard returns 403 `PASSWORD_CHANGE_REQUIRED` except on routes marked `@AllowDuringPasswordChange()`). Demo role cards (`/demo/login`) only open the seed tenants. Never log, return twice, or store a password in clear text; a temp password is shown exactly once. Sessions slide: activity (guard, at most once a minute) extends `expires_at` by `SESSION_TTL_HOURS` (12) but never past `created_at + SESSION_MAX_HOURS` (14); the cookie lives `SESSION_MAX_HOURS`.
- **Telegram bot** (`apps/api/src/telegram/*`): booking rules live in `modules/booking.ts` and are shared with the staff API — never duplicate them in the bot. Patient notices go through the `notifications` outbox (`enqueueNotice` inside the event's transaction). Never send lab values, clinical text or another patient's data to Telegram; a chat sees only patients with its verified phone. Bot tokens are stored only encrypted (`core/secrets.ts`, `APP_SECRET_KEY`). Test the bot through the simulator transport or the fake Bot API in `test/telegram.test.mjs` — no real Telegram in tests. Free-text questions about the clinic go through `telegram/faq.ts` only (AI route `bot_faq`, after COMMIT): knowledge from the clinic's reference data and the manager's extra text, never the person's card or appointments; medical questions get the fixed «ask a doctor» text without a model call; every number in a model answer must be in the knowledge or the reply is «ask the registrar»; only daily counts are stored (`docs/AI.md`).
- **Cash desk:** a payment needs the payer's *own* open shift in the invoice's branch (lock it `FOR SHARE`) — a cashier or the manager may open a shift and take money (`canTakeMoney()` in the web mirrors the server roles); a shift opened before today's local day start is stale: `/cash-shifts/current` returns `stale: true` and a payment gets 409 `SHIFT_STALE` until it is closed (Z-report = one day). Refunds are manager-only, tied to a payment, reduce the invoice (`credit_amount`, `paid_amount` stays ≤ `total`) and cash refunds/expenses must name an open shift. Revenue is cash basis and **net of refunds** everywhere (dashboard, finance summary, AI report). Shifts, refunds and expenses are append-only/void-only via DB triggers. Use `invoiceStatus()` from `billing.ts` for invoice status and `NET_LINE` for any per-service money (doctor share, service revenue) so refunds are excluded. Doctor share: `service_orders.share_percent_snapshot` is set once at order creation by `sharePercentFor()` — the performing doctor's `doctors.default_share_percent` when it is > 0 (0 = not set), otherwise the service's `share_percent`; later edits never change past orders. Cash may leave a drawer only if it is there (`INSUFFICIENT_CASH`). **Fiscal receipts** (`fiscal/provider.ts`, migration 023): every payment/refund gets exactly one `fiscal_receipts` row created inside the same transaction via `recordFiscal()` — provider `manual` (production default, parallel mode: the cashier types the certified KKM receipt number, `POST /payments/:id/fiscal`) or `none` (demo, `skipped`); a provider error never blocks the sale (row `failed`); issued/skipped rows are immutable (trigger); gate fiscal UI on `me.fiscal_provider !== 'none'`; services carry `ikpu_code` (17 digits), `vat_percent`/`vat_exempt`, `package_code`.
- **Quantity, line refunds, deposits, debtors (migration 024):** an order carries `quantity` (1–50; > 1 only for a `procedure` — a lab test or a scan has one result), `price_snapshot` stays the unit price and the invoice line is `qty × price` (`createBilledOrder({ quantity })`, `ordersCreateSchema` takes `items: [{service_id, quantity}]`; the old `service_ids` still works). A refund may name one line (`order_id`): that line's `invoice_items.refunded_amount` grows (CHECK ≤ `line_total`), `invoices.line_refunded_amount` sums them; a refund without `order_id` is spread proportionally as before — `NET_LINE` handles both, so always use it (never `line_total`) for per-service money. **Deposits** (`patient_deposits`, append-only: `in` by a cashier in their open shift, `apply` through `POST /invoices/:id/payments` with `method: 'deposit'`, `out` by the manager from an open drawer) are a **liability, not revenue**: revenue stays the cash-basis sum of payments (the applied amount is a payment at the moment it is applied) minus refunds, so deposit money counts exactly once; before reading a balance lock the patient row `FOR UPDATE` (`applyDeposit()` in `modules/deposits.ts`; the DB trigger refuses a negative balance anyway); cash deposits move the drawer (`ShiftTotals.deposit_in/deposit_out`). Debtors: `GET /invoices?debt=1` returns `meta.ageing` (0–7 / 8–30 / 31+ days since the invoice) and takes `age=`, a cashier or the manager sets `promise_date` + note (`POST /invoices/:id/promise`). Every CSV export goes through `core/csv.ts` (period ≤ 1 year via `csvPeriod`, `csvCell` neutralises formulas, Tashkent time) and ends with a totals row; every money list is paginated (`pageParams`).
- **Demo reset truncates every table** and refuses to run when a non-seed tenant exists. Real clinics belong in a separate `APP_MODE=production` deployment on a server in Uzbekistan (`Dockerfile`, `deploy/`, runbook `docs/DEPLOY_UZ.md`); there the API refuses a database with a demo clock, and the UI shows no «demo» wording (gate demo-only text on `me.demo`).
- **Hikvision cameras** (`apps/api/src/cameras/*`, `docs/HIKVISION.md`): faces and templates stay in the camera's own library; Med.uz.ai stores only our codes (`S-n` staff, `P-<patient number>` patients), event times and similarity — never face pictures or raw payloads (the parser drops image parts unread). The one exception is the **alert snapshot** (`camera_snapshots`, migration 016): the camera's picture of a *security alert* (intrusion, line crossing, region entry/exit, loitering, tamper that raised an alert), kept only when the camera's `alert_snapshots` is on, ≤ 1 MB, purged after `SNAPSHOT_DAYS` (30), readable only by the manager and the guard of the alert's branch («rahbar va qorovul (o‘z filiali)»; the full picture is audited on every view, the feed's blurred thumbnail `/security/alerts/:id/thumb` is not) — never for `face_match`/`people_count` and never for a non-alert event. The demo's snapshots (`database/seed/snapshots`) are built by `tools/make-snapshots.py` from freely licensed stock photos (`tools/snapshot-sources/ATTRIBUTION.md`) with every face and sign pixelated first — never pictures from a real camera or of real patients. Staff codes need the manager's confirmation of written consent; patients need an active `biometric` consent (signed paper only). Cameras push to `POST /api/v1/hik/<token>` (only the token hash is stored). A camera can also be connected directly over ISAPI (`cameras/isapi-client.ts`, `isapi.controller.ts`, `pull-worker.ts`): Digest auth, password encrypted with `APP_SECRET_KEY`, one-click setup writes the listening host (fresh token, shown to nobody) and creates the face library, faces are forwarded to the camera from memory and never stored (`face_code_cameras` keeps only code↔camera), revoked codes are deleted from cameras by the worker, `delivery='pull'` reads `alertStream` server-side. TLS to a camera is verified (no self-signed bypass). Tests use the fake camera `test/_fakecam.mjs` — never a real device. Camera arrival is only a suggestion; accepting it runs the normal check-in. Events are append-only. Real cameras connect only to a server in Uzbekistan; the demo uses the simulator.
- **Note templates & quick phrases** (`note_templates`, `quick_phrases`, migration 025, `modules/templates.controller.ts`) are clinic interface text, not patient data: doctors and managers read them, other roles 403. Starter templates are a static list (`database/seed/templates.ts`, outside the seed PRNG) inserted by `ensureStarterTemplates` (create-clinic, demo reset, API start; idempotent by `starter_key`). Applying a template fills only empty fields unless the doctor chooses, ICD codes are re-checked on save, proposed orders are a checkbox list sent through the normal orders endpoint — never auto-ordered. A doctor's follow-up booking uses `booking.ts` with `source='doctor'` and only for themselves.
- **Warehouse** (`modules/warehouse*.ts`, migration 030, `docs/WAREHOUSE.md`): role `storekeeper` sees only the warehouse (+ own profile) — never a patient card, visit, note or invoice (server 403); doctors/lab only request and see their own requests. Stock = Σ `inventory_batches.qty`; keep `opening_qty + Σ ledger = Σ batches` (tests check it). Every quantity change runs in `db.tx`, locks the item rows `FOR UPDATE` (sorted) first, then reads batches; issue is FEFO and never touches an expired batch. Every `issue`/`return` row names **who took it** and **what for** (patient visit + ICD-10 codes taken from the note — codes only, never note text — or a procedure order, or a department): DB CHECKs enforce it. `inventory_movements` is append-only (void once, with a reason, manager only, reversal row); batches change only their balance. Controlled items: manager approves the request, a different person issues; write-off acts need ≥ 3 commission members and an approver who did not draw up the act. Patients are not billed for materials.
- **Security guard** (role `guard`, migration 038, `modules/security*.ts`, `docs/SECURITY_GUARD.md`): the guard sees only `/security/*` (+ `/me`, own-branch `/branches`, `/rooms`) — every patient, appointment, clinical, finance, warehouse, settings, doctors/services route is 403 (`test/guard.test.mjs` sweeps them). A patient's face match is only «Bemor» (no code/name), patient flow only counts; staff matches show name + position. Alert handling is append-only `security_alert_actions` with `seq` (lock the event `FOR UPDATE`, stale → 409); `escalated` is closed only by the manager; a final resolve also writes `camera_event_acks`. The guard reads alert snapshots only for security alerts ≤ 30 days (full view audited, list thumbnail not). Migration 040: one open-items definition (`guard_open_items()` SQL; alerts/incidents bounded by `SECURITY_OPEN_DAYS` 30 everywhere), snapshot stored on the shift at close (print uses it), manager `force-close` with a reason (reason never in audit), stale shift > 26 h, rounds freeze `checkpoint_ids` and need an open shift (409 `SHIFT_REQUIRED`), «Kechikkan» alerts (10 min new / 30 min taken) → guard list + manager alarm, SOS dedupe 60 s + optional `Idempotency-Key`, visitors auto-closed after 24 h, `ID_DOCUMENT_RE` on every guard text; guard action buttons use `useGuardedMutation` (in-flight guard). Incidents/entries, keys, patrol marks, presence marks are append-only (triggers); shifts/rounds close once; visitors change only «out once» and the 90-day purge of personal fields (`purgeVisitors`, hourly) — never a passport/JShShIR. Free text goes through `redact()`; audit never carries it. Seed: `database/seed/guard.ts` on its own PRNG + `backfillSeedGuard`.
- **Patient consent** (`patient_consents`, `modules/consent.ts`) is append-only evidence; a withdrawal is a new row. Production requires data-processing consent when a card is created (422 `CONSENT_REQUIRED`). The consent texts are versioned (`CONSENT_TEXT_VERSION`) and need a lawyer's review — change the version when the text changes. **Data-subject requests** (`modules/erasure.ts`, migration 026): `GET /patients/:id/card` (role-filtered print, diagnosis doctor-only), `GET /patients/:id/export.json` (manager only, audited, 5/min per tenant, a sealed download the UI never renders) and `POST /patients/:id/anonymise` (manager, reason required, 409 `ERASURE_BLOCKED` while debt/deposit/future visit exist). Erasure = anonymisation, never deletion: names → «Anonim bemor #n», contacts/birth date cleared, consents get withdrawal rows, own Telegram chat unlinked; notes, results, documents, invoices stay under the anonymous card (retention law) and the DB trigger forbids a restore. Anonymised cards are out of name/phone search, booking and the bot (`OWN_CARD_SQL`).
- **DMED / DHP** (`apps/api/src/dhp/*`, migration 029, `docs/DMED_INTEGRATION.md`): clinical events enqueue a FHIR transaction Bundle with `enqueueDhp()` inside their own transaction (only when `dhp_settings.mode ≠ off`); no complaints/examination text in bundles; the token is write-only and encrypted; identifier systems are constants in `dhp/fhir.ts`; tests use the fake FHIR server in `test/dhp.test.mjs` — never a real DMED/UZINFOCOM endpoint.
- **Drugs & allergies** (migration 028, `docs/DRUGS.md`): `drugs` is a global INN list (starter `database/seed/drugs.csv` loaded on migrate while empty — clinical review pending; `db:import-drugs` for an official list; generic names only, never brands), `patient_allergies` is append + confirm/withdraw only (trigger). Every prescription goes through `checkPrescription()` (`modules/allergy-check.ts`): severe hit → 409 `ALLERGY_CONFLICT` unless `override_reason` (kept in the document, audited without the text); registrars record only free text («bemor aytdi») and never read the list.
- **AI calls go only through `AiClient.json()`** (`apps/api/src/ai/ai-client.ts`): provider `AI_PROVIDER=anthropic` (official SDK) or `gemini` (REST generateContent), structured JSON validated with zod, refusal/error mapping, Uzbek apostrophes normalized, one `ai_usage` row per call (tokens + cost, never text). Tests use the fake Claude/Gemini/PubMed servers in `test/ai.test.mjs` — never a real key.

## Data & environments

- Local Postgres: docker `meduza-db` on 127.0.0.1:5433 — `meduza` = live demo shown to clinics, `meduza_test` = tests/E2E only. Tests refuse non-`_test` databases; keep it that way.
- Seed is deterministic (fixed PRNG + hashed ids). Changing RNG call order shifts seeded numbers — then update the expected KPIs in `docs/DEMO_SCRIPT.md`, `meduza-demo-reset` and tests.
- Railway (`feisty-amazement`, service `meduza` + `Postgres`, region US): password-gated demo, synthetic data only. Real patient data or biometrics must not go there — Uzbek law requires biometric data to be stored in Uzbekistan.
- Never commit or print `.env`, `backups/*.dump`, `DEMO_ACCESS_CODE`, tokens or keys.
